# Category Contract — Referent-First Classification

Categories exist to keep a traversed stack recoverable.

They are **local relational projections**, not permanent boxes imposed on reality.

## Core rule

At any category level:

> **siblings must answer the same question.**

If the question changes, descend another layer or create a separate projection.

Do not mix axes.

Bad:

```text
artifacts
├─ software        ← medium/domain
├─ CAD             ← representation form
├─ tested          ← witness depth
└─ paid            ← goal/status
```

Good:

```text
artifact
└─ preserved relation
   ├─ structural
   ├─ behavioral
   └─ observational
```

Then each child may be decomposed again under a new explicit local axis.

## Referent-first category movement

A category is admitted from a parent only when the current relation supports it:

```text
parent referent
    ↓
what distinction is required here?
    ↓
declare one local axis
    ↓
derive child categories from actual relations
    ↓
place item at the narrowest supported child
    ↓
repeat if another distinction is required
```

The output of one categorization remains a valid referent for another categorization.

## Rules

### 1. One axis per sibling set

A sibling set must be generated by one stated relation.

Examples:

- **why work exists** → research / open source / paid;
- **what relation an artifact preserves** → structural / behavioral / observational;
- **how deeply a claim is witnessed** → represented / modeled / simulated / built / measured;
- **what dependency is required** → whatever the current referent actually opens.

### 2. Do not pre-fill empty reality

Categories are open-ended.

Do not invent branches merely to make a taxonomy look complete.

A new child is added when traversal reaches a relation that existing children do not preserve.

### 3. Domain labels are not automatic parents

"Mechanical", "software", "electrical", "chemistry", etc. may identify a dependency layer, but they do not own the work.

A problem crosses those labels as needed.

### 4. Status is not type

Witness depth, completion state, payment state, and validation state must not be mixed into artifact/capability type trees.

### 5. A child remains decomposable

No category is treated as terminal merely because humans normally assign it to one specialty.

Example:

```text
structural artifact
→ spatial relation
→ object/local reference frame
→ CAD-like artifact
→ assembly
→ component
→ interface
→ dimension
→ tolerance
```

Each reached node may be opened again.

### 6. Preserve cross-links instead of duplicating categories

One artifact can participate in several relations without being copied into several incompatible trees.

Keep one canonical artifact and project it separately by:
- representation category;
- dependency layer;
- witness depth;
- capability;
- goal lane;
- downstream relation.

## Repository category axes

These axes remain separate:

| Layer | Local categorization question |
|---|---|
| current problem | What required relation/dependency opened? |
| capability | What broad problem-space has repeated evidenced closure? |
| artifact | What relation does this artifact primarily preserve? |
| dependency | What part of the current referent requires this layer? |
| witness | How deeply is this relation actually evidenced? |
| goal lane | Why is this work being done? |
| view | What read-only projection is being requested? |

These are projections over the same work. They are not one flat taxonomy.

## Tidy invariant

A category path should be readable as a chain of relations, not as a pile of labels.

```text
artifact
→ preserves behavior
→ executable behavior
→ program
```

```text
artifact
→ preserves structure
→ spatial structure
→ CAD-like
```

```text
artifact
→ preserves observation
→ empirical witness
→ test / measurement
```

If a path cannot be read relationally, the categorization should be reconsidered.
