# Complete Stack

## Referent

This repository exists to build and preserve **complete-stack problem-solving capability**.

"Complete stack" does not mean full-stack web development.

It means:

> Given a real problem, keep traversing every required dependency layer until the stack needed for a valid solution is represented, evidenced, realized, or explicitly walled.

A problem may begin in software and open into physics.
A physical machine may open into electronics, controls, software, materials, manufacturing, cost, safety, and regulation.
A research problem may open into mathematics, simulation, instrumentation, fabrication, and measurement.

The field boundary never becomes an excuse to stop.

## A/B relation

A/B remains the recursively reusable mathematical operation and witness/evidence contract.

Complete Stack is an application orientation over problems.

Do not redefine A/B as:
- this repository;
- a workflow;
- a software runtime;
- a capability map;
- a project manager;
- a "complete stack" methodology.

The repository preserves evidence of repeated movement through real dependency structures.

## Category discipline

Category paths follow [CATEGORY_CONTRACT.md](CATEGORY_CONTRACT.md): one local axis per sibling set, derived from the relation actually reached. Categories remain recursively decomposable and separate from witness/status/goal labels.

## Stack traversal

For any problem:

```text
current referent
    ↓
relations actually required
    ↓
dependency opens
    ↓
enter that layer
    ↓
represent / model / build / measure / test
    ↓
emit required working artifact(s)
    ↓
preserve witness + provenance
    ↓
return result as valid input
    ↓
continue
```

Traversal can move horizontally across fields and vertically through realization depth.

When a relation needs to become inspectable or reusable, traversal emits a working artifact. Code, CAD-like geometry, system landscapes, equations/models, schematics, BOMs, and test/measurement packages are sibling representations at this layer. See [artifacts/README.md](artifacts/README.md).

## Layer status

Every reached layer must be explicit about what exists.

Examples:

```text
unknown
researched
represented
modeled
simulated
designed
implemented
built
measured
inspected
validated
deployed / operating
```

Do not collapse these states.

A physical part may temporarily be represented digitally by measured or justified interfaces so surrounding work can continue. The placeholder does not become the physical witness.

Example:

```text
battery pack
→ voltage/current/capacity/mass/dimensions/thermal/interface model
→ surrounding systems can be designed
→ real pack data later replaces placeholder
→ rerun affected relations
```

This is allowed because the missing layer remains visible.

## Capability proof

A capability is not proved by naming a field.

It is strengthened by showing that different problems within a problem-space can be traversed through their required stacks without relying on one fixed implementation.

### First broad capability — Programs

The program foundation is the first serious proof.

It has demonstrated reusable structure for:
- unlike program shapes;
- typed input/output relations;
- composition;
- generic relation graphs;
- bounded recurrence;
- execution/value lineage;
- external effect/port admission.

Those witnesses mean the repo is no longer centered on copying individual applications. They are evidence that arbitrary bounded program problems can increasingly be represented and realized through shared structure.

The program foundation is now **frozen as a capability proof** unless a future problem exposes a missing relation that requires reopening it.

## Next capability expansion

The next major expansion should force the same movement through non-digital layers.

A strong target class is **machines / physical products / integrated physical systems** because one object can require:

```text
requirements
→ geometry
→ mechanics
→ materials
→ energy
→ electronics
→ sensing
→ controls
→ embedded software
→ communications
→ interfaces
→ thermal behavior
→ manufacturing
→ tooling
→ testing
→ safety
→ cost
→ service
→ regulation
```

The objective is not to claim a physical build where none exists.

The objective is to preserve the complete dependency stack so unavailable physical relations can be represented honestly, surrounding work can proceed, and physical witnesses can replace placeholders later.

## Core invariant

**Do not stop because the next dependency belongs to another discipline.**

Stop only when:
- the required relation is solved/witnessed;
- the relation is represented with an explicit justified placeholder that permits valid continuation;
- or a real wall is reached and recorded.
